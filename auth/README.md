# Вход и регистрация Career Quest

Основной `app.py` использует настоящие аккаунты и локальную SQLite. После скачивания репозитория каждая установка создаёт свою базу; подключение к внешнему серверу БД не требуется. Страница оформлена в общем светло-зелёном стиле проекта.

## Запуск и первый администратор

Из корня репозитория, после создания виртуального окружения с Python 3.11+:

```bash
python -m pip install -r requirements.txt
python -m streamlit run app.py
```

Откройте [http://localhost:8501](http://localhost:8501). На чистой установке появляется форма первого администратора: задайте имя, почту и пароль самостоятельно. После создания аккаунта администратор автоматически входит в «Пользователи»; последующие пользователи входят или регистрируются. Готовых логинов и стандартных паролей нет. SQLite, scrypt и генератор токенов входят в стандартную библиотеку Python; сборка Python должна поддерживать `hashlib.scrypt`.

Сервер по умолчанию слушает только `127.0.0.1`. Первый запуск выполняет владелец компьютера: до создания первого администратора именно первая успешная отправка формы получает эту роль.

## Роли и связь с профилем

| Роль | Как получить | Доступ |
| --- | --- | --- |
| Сотрудник (`employee`) | Зарегистрироваться на странице | Собственный профиль после привязки администратором |
| HR (`hr`) | Администратор назначает роль существующему аккаунту | Заявки и решения, оценки, обзор команды |
| Администратор (`admin`) | Первый запуск; далее роль назначает администратор | Пользователи, импорт и состояние приложения |

На форме входа выберите роль и введите почту/пароль. Выбранная роль должна совпасть с сохранённой в БД: сам переключатель прав не выдаёт. Публичная регистрация всегда создаёт сотрудника без привязки к данным. Имена и почта не используются для автоматического сопоставления.

Администратор открывает **«Пользователи»**, выбирает зарегистрированный аккаунт, назначает роль и при необходимости профиль по `employee_id`. До привязки сотрудник видит сообщение о необходимости настройки и не получает доступ к чужому профилю. Один профиль можно связать не более чем с одним аккаунтом; можно снять привязку. Профиль должен существовать в загруженном dataset, в том числе после импорта.

Сохранение новой роли или привязки отзывает все сессии изменённого аккаунта. Пользователь входит заново; при сохранении без изменений сессии остаются. Последнего активного администратора нельзя понизить. Управление пользователями проверяет роль администратора в БД.

### Локальные команды владельца установки

Создать первого администратора можно также в терминале; имя и почта вводятся интерактивно, пароль скрыт:

```bash
python -m auth.manage create-admin
```

Назначить роль уже зарегистрированному аккаунту:

```bash
python -m auth.manage set-role --email person@example.org --role hr
```

Допустимы `employee`, `hr`, `admin`. Это команды доверенного владельца компьютера с доступом к файлу БД. Параметр `--db` перед подкомандой выбирает конкретный файл. Для связи с профилем используйте веб-раздел «Пользователи».

## Хранение и сессии

- База автоматически создаётся в `.career-quest/accounts.sqlite3`. Общая папка задаётся `CAREER_QUEST_DATA_HOME`, конкретный файл — `CAREER_QUEST_AUTH_DB`. Относительные пути отсчитываются от корня проекта. При стандартных путях, если уже существует `auth/.local/auth.sqlite3`, используется прежняя база: аккаунты не переносятся в пустой файл. Отличная от стандартной папка `CAREER_QUEST_DATA_HOME` задаёт отдельную установку, а конкретный `CAREER_QUEST_AUTH_DB` имеет приоритет над ней.
- `.env` из корня читается автоматически; переменные окружения процесса имеют приоритет. Не храните секреты в отслеживаемых файлах. Базы, их служебные файлы и `.env` исключены из Git.
- Пароли длиной 15–128 символов хешируются с индивидуальной случайной солью: scrypt, `N=2^17`, `r=8`, `p=1`. Открытые пароли не сохраняются. Один расчёт использует около 128 МБ памяти; внутри процесса расчёты выполняются по очереди.
- Почта нормализуется, уникальность обеспечивается SQLite. Формы проверяют подтверждение пароля; ошибки показаны по-русски.
- Ошибка входа одинакова для неизвестной почты, неверного пароля, роли и неактивного аккаунта. После пяти ошибок за 15 минут вход по этой почте ограничивается на 15 минут. Счётчики сохраняются при перезапуске; отдельного журнала событий входа нет.
- Случайный токен сессии находится в серверном `st.session_state`, в SQLite — только его SHA-256. Сессия действует до 8 часов, максимальный простой — 30 минут. Каждое выполнение страницы повторно проверяет сессию; выход отзывает токен.
- Аккаунты, роли и привязки сохраняются после перезапуска. Полная перезагрузка вкладки может сбросить сессию Streamlit: нужно войти снова. Cookies «запомнить меня» не реализованы.
- Пароли и токены не выводятся в журнал. Сведения для входа не передаются AI-провайдерам.

Для резервной копии остановите сервер и скопируйте всю папку `.career-quest/`, а при использовании старой базы — ещё `auth/.local/`. При явных путях сохраните соответствующие файлы. Восстанавливайте связанные БД из одного комплекта при остановленном сервере. Копия содержит аккаунты и персональные данные; не публикуйте её в GitHub. Полный порядок запуска и описание остальных БД — в [README проекта](../README.md).

## Демонстрационный и самостоятельный режимы

По умолчанию `CAREER_QUEST_DEMO_MODE=0`: вход проверяет аккаунты. Только явное `CAREER_QUEST_DEMO_MODE=1` включает свободный выбор роли и профиля через `demo_ui.py` / `demo_session.py`. Этот режим нужен для показа и тестов, **не является разграничением доступа**. Импорт и завершения маршрута в нём живут в сессии; HR-функции продолжают использовать SQLite. Укажите отдельную `CAREER_QUEST_DATA_HOME`, чтобы демонстрационные действия не меняли рабочие HR-данные.

`python -m streamlit run auth_app.py --server.port 8503` запускает самостоятельную страницу входа/регистрации, без рабочих разделов Career Quest. Для полного сценария используйте `app.py`.

## Файлы

```text
app.py                  вход и рабочие разделы приложения
auth_app.py             отдельная страница проверки аккаунтов
storage/config.py       .env и пути локальных баз
auth/
  service.py            аккаунты, роли, привязки, SQLite и сессии
  manage.py             локальные команды управления ролями
  ui.py                 формы входа и регистрации
  integration_ui.py     первый администратор и управление пользователями
  styles.css            оформление страницы авторизации
  demo_session.py       явный демонстрационный выбор роли/профиля
  demo_ui.py            страница демовхода
  checks/               проверки сервиса и Streamlit-форм
```

## Проверка

```bash
python -m unittest discover -s auth/checks -p "test_*.py" -v
python -m unittest discover -s ui/checks -p "test_*.py" -v
```

Тесты должны работать с временными БД и явно тестовыми аккаунтами. Ручной сценарий: чистая установка → первый администратор → регистрация сотрудника → привязка профиля администратором → вход сотрудника → собственный профиль → выход → попытка входа как HR с теми же данными (отказ). Назначить HR администратором, войти заново с этой ролью. После остановки и повторного запуска проверить сохранение аккаунтов и привязок.

## Ограничения

Это локальный прототип, не корпоративная IAM-система. Нет проверки владения почтой, восстановления пароля, SSO или MFA. Публичная регистрация доступна любому, кто может открыть сервер. Администратор сопоставляет аккаунты с профилями вручную. SQLite рассчитана на один локальный экземпляр приложения; серверная файловая система является границей доверия. Резервную копию и права на папку БД обеспечивает владелец установки.

Для публичного размещения потребуются HTTPS, корпоративный провайдер идентификации или приглашения и ограничение нагрузки на уровне прокси. Ограничение попыток по почте не заменяет защиту от распределённой нагрузки. Явный демонстрационный режим для такого размещения не подходит.
