# Вход и регистрация Career Quest

Страница в светлом зелёном стиле Career Quest. Самостоятельный режим `auth_app.py`: вход сотрудника, HR или администратора, регистрация сотрудника, подтверждение входа и выход. Интегрированный режим `app.py`: демонстрационный вход в рабочие разделы без базы аккаунтов. Движок `core/` сохраняется без изменений.

**Обновление интеграции:** `app.py` теперь начинает с этой же визуальной страницы в демонстрационном варианте (`demo_ui.py` + `demo_session.py`). Он позволяет выбрать роль и реальный профиль кита без пароля и без вызова `AuthService`. Роли открывают соответствующие рабочие разделы; выход возвращает на форму, сохраняя сценарий в текущей вкладке. SQLite для аккаунтов в этом пути не используется. Существующее хранилище сертификатов, решений HR и бюджета AI остаётся частью модуля развития. Настоящая регистрация ниже по-прежнему запускается отдельно через `auth_app.py`.

## Запуск

Из корня репозитория, Python 3.11+ и установленные зависимости основного проекта:

```bash
python -m pip install -r requirements.txt
python -m streamlit run auth_app.py --server.port 8503
```

Страница: `http://localhost:8503`. Проверена на Python 3.14 и Streamlit 1.64. Новых зависимостей нет; SQLite, scrypt и генератор токенов входят в стандартную библиотеку Python. Установка Python должна поддерживать `hashlib.scrypt`.

## Роли и аккаунты

| Вариант входа | Сохранённая роль | Как получить |
| --- | --- | --- |
| Сотрудник | `employee` | Зарегистрироваться на странице |
| HR | `hr` | Зарегистрироваться; владелец сервера назначает роль |
| Администратор | `admin` | Первый аккаунт создаётся серверной командой; дальнейшие роли назначаются на сервере |

Выбор роли при входе не выдаёт права: почта, пароль и выбранная роль должны соответствовать записи в базе. Публичная регистрация не принимает роль. Один аккаунт имеет одну роль.

Создать первого администратора (имя и почта вводятся интерактивно, пароль скрыт):

```bash
python -m auth.manage create-admin
```

Назначить роль уже зарегистрированному аккаунту:

```bash
python -m auth.manage set-role --email person@example.org --role hr
```

Допустимы `employee`, `hr`, `admin`. Эти команды предназначены владельцу сервера, имеющему доступ к файлу БД; веб-интерфейс их не вызывает. Смена роли отзывает прежние сессии. Последнего активного администратора нельзя понизить. Готовых аккаунтов и стандартных паролей в репозитории нет.

## Хранение и защита

- База создаётся автоматически в `auth/.local/auth.sqlite3`; `.gitignore` исключает её и сопутствующие файлы. Путь переопределяется переменной `CAREER_QUEST_AUTH_DB` или параметром `--db` перед серверной командой.
- Пароли длиной 15–128 символов хешируются с индивидуальной случайной солью: scrypt, `N=2^17`, `r=8`, `p=1`, по [рекомендации OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Открытые пароли не сохраняются. Один расчёт использует около 128 МБ памяти; в одном процессе расчёты выполняются по очереди.
- Почта нормализуется, её уникальность обеспечивается SQLite. UI проверяет подтверждение пароля, ошибки представлены по-русски.
- Ошибка входа одинакова для неизвестной почты, неверного пароля, роли и заблокированного аккаунта. После пяти ошибок за 15 минут вход по этой почте ограничивается на 15 минут. Счётчики сохраняются при перезапуске; это не журнал событий.
- Случайный токен сессии находится в серверном `st.session_state`, в SQLite хранится только его SHA-256. Время жизни: 8 часов, простой: 30 минут. Каждое выполнение страницы повторно проверяет сессию. Выход отзывает токен.
- База сохраняет аккаунты при перезапуске приложения. Перезагрузка вкладки может сбросить сессию Streamlit: предусмотрен повторный вход, постоянных cookies и функции «запомнить меня» нет.
- Пароли, токены и события входа не записываются в журнал. Данные аккаунтов не отправляются внешним API.

## Подключение ко второй версии приложения

`render_auth()` из `auth.ui` возвращает проверенный словарь `{user_id, name, email, role, active}` или `None`. Схема точки входа:

```python
user = render_auth()
if user is None:
    st.stop()
# Затем серверное определение допустимого раздела по user["role"].
```

`setup_page()` подключает самостоятельное оформление и шапку. Для текущей отдельной страницы `render_account(user)` показывает результат входа и кнопку выхода. Выбранная роль не хранится как доверенный признак: сервис читает актуальную роль из БД. Хост-приложение должно проверять сессию и права перед каждой операцией, а не только скрывать вкладки.

**Рабочие пространства подключены к демонстрационному входу, но пока не к настоящим аккаунтам.** Основной `app.py` выбирает роль и профиль через `render_demo_login()`; сотрудник видит только выбранный на входе профиль до выхода. Это удобство демонстрации, не защита данных: любую роль можно выбрать на странице. Аккаунт не связывается автоматически с профилем из датасета по имени или почте. При дальнейшей интеграции требуется явное серверное соответствие `user_id → employee_id` и отдельная проверка прав HR/администратора на каждое действие.

## Проверка

```bash
python -m unittest discover -s auth/checks -p "test_*.py" -v
```

Тесты используют временные БД и явно тестовые аккаунты. Проверяются регистрация, нормализация и уникальность почты, хранение хешей, три роли, отказ при несовпадении роли, неверные данные, ограничение попыток, отзыв и истечение сессий, создание первого администратора, конкурирующая регистрация и поведение форм.

Ручной сценарий: зарегистрировать сотрудника → войти с его почтой и паролем → увидеть своё имя и роль → выйти → попытаться войти как HR с теми же данными (отказ). Назначить HR серверной командой и повторить вход с ролью HR. Первого администратора создать через `create-admin` и войти как администратор.

## Ограничения

Это локальный прототип учётных записей, не готовая корпоративная IAM-система. Нет проверки владения почтой, восстановления пароля, SSO, MFA, UI администрирования или привязки к реальным сотрудникам. Регистрация открыта всем, кто имеет доступ к странице. Для публичного развёртывания нужны HTTPS, корпоративный провайдер идентификации или приглашения, ограничение запросов на вход и регистрацию на уровне прокси, защищённые права на каталог БД и резервное копирование. Ограничение попыток по почте не заменяет защиту от распределённой нагрузки. SQLite рассчитана на один экземпляр прототипа.
